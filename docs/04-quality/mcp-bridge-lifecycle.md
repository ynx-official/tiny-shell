# MCP 桥接进程退出验证

> 状态：Review
> 最后更新：2026-10-22
> 关联：[MCP 开发契约](../03-architecture/mcp-contracts.md#桥接进程生命周期)、[源码运行桥接回归](mcp-cargo-run-bridge.md)

## 问题与验收目标

外部 MCP 总开关关闭后，客户端启动的独立桥接仍等待 stdio 输入并保留运行时线程。两个桥接入口应在禁用状态下立即退出，并在握手中或握手完成后检测到关闭时自动结束，不要求客户端先断开输入管道。完整行为以开发契约为准。

这次修复限于桥接源码、回归和文档；用户明确要求先不要编译。没有启动、替换或终止当前安装版及其桥接进程。

## 新增回归代码

`crates/mcp/tests/stdio.rs` 使用隔离目录、真实 helper 子进程及管道：

| 场景 | 断言 |
| --- | --- |
| 禁用时重复启动三次 | 每次均在五秒期限内正常退出，stdout/stderr 为空，客户端 stdin 始终保持打开 |
| 策略文件缺失 | 默认关闭，不等待握手 |
| initialize 已回复但客户端尚未发送 initialized | 关闭开关后自行退出，不等待剩余握手输入 |
| 同一配置存在两个已初始化桥接 | 关闭后两个实例均退出 |
| 另一独立配置同时启用 | 关闭第一份配置后，另一配置仍可正常列出十个工具 |
| 关闭后再次启动、随后重新启用 | 关闭时立即退出，重新启用后新桥接可完成握手和工具发现 |
| 撤销已连接的客户端 | 该客户端桥接退出，其他注册仍可工作 |
| 已连接时策略损坏 | 桥接以失败状态退出，不能继续驻留 |

`tests/mcp_embedded_stdio.rs` 将主应用复制到没有 helper 的隔离目录，覆盖 `--mcp` 入口的禁用启动、握手未完成和握手已完成后的主动退出。原有离线应用握手测试显式启用 MCP，继续验证十个工具、结构化 `APP_NOT_RUNNING` 和 EOF 退出，不削弱原有断言。

退出断言特意将写入端取出并持有到子进程结束之后，避免测试框架自动关闭 stdin 掩盖运行时退出阻塞。子进程均启用 `kill_on_drop`，超时失败时回收测试进程。

先添加回归代码，再修改共享入口；因用户禁止编译，未运行修复前失败或修复后通过的测试，不把代码检查当作 TDD 红绿证据。

## 检查记录

- 已执行：修改的三个 Rust 文件经 rustfmt 格式化；`cargo fmt --all -- --check` 通过，不触发编译。
- 已执行：限定本轮修改文件的 `git diff --check` 通过；三个相关文档的本地文件链接检查通过。
- 未执行：`cargo check`、`cargo test`、Clippy、构建、打包、应用启动及原生验收；原因是用户要求先不要编译。
- Windows、macOS、Linux 的实际进程退出行为均待运行验证。

实现依据包括锁定的 rmcp 3.4.0 本地源码，以及 Tokio 的 [stdin 阻塞读取说明](https://docs.rs/tokio/latest/tokio/io/fn.stdin.html)和[运行时限时退出说明](https://docs.rs/tokio/latest/tokio/runtime/struct.Runtime.html#method.shutdown_timeout)。限时关闭运行时只解除调用线程的等待；两个二进制入口随后结束进程，由操作系统释放剩余线程。

## 更新程序后的手动验收

1. 在设置 → MCP / CLI → 外部 MCP 中启用 MCP，让客户端连接并成功列出工具；记录对应桥接 PID。保持客户端打开，关闭 MCP，预期这些新版本桥接在五秒内退出。
2. MCP 保持关闭，在客户端重复重连或打开多个会话，预期不能建立服务、后台无持续存活的新桥接。第三方重试期间可能出现立即退出的短暂进程。
3. 重新启用 MCP，在客户端重新连接，预期工具发现和授权范围内调用恢复；再次关闭后仍能退出，无累积驻留。
4. 同时连接两个客户端，仅撤销其中一个注册，预期对应桥接退出，另一个仍可列出工具。若使用不同配置目录，关闭其中一份也不影响另一份。
5. 检查主程序 `--mcp` 备用入口与独立 helper 行为一致；内置 AI 的独立 SSH 权限及普通终端连接不受外部 MCP 关闭影响。

验收需要更新后的二进制。现有旧进程需要在更新时由客户端断开、退出或重启后清理，不能用本轮源码变更宣称已经释放当前后台资源。
